1五個面向，一個都跑不掉 | The Five Dimensions

功能正確性

程式是否可執行、核心功能是否達成——最基本的一關。

Git 使用品質

commit 頻率、訊息品質、分支使用是否合理（呼應 KP-10）。

AI 使用透明度

PROMPTS.md 完整度、提示詞層次、自身檢查判斷（呼應 KP-09）。

程式碼品質

結構、可讀性、必要的測試——你是否真正消化了 AI 產出。

文件完整性

README、系統架構說明是否清楚——讓陌生人看得懂。

2反過來指導日常開發習慣 | Guiding Your Daily Habits

評分標準不是等交作業那天才出現的東西，它應該是你每天做決定時心裡那把尺。
1
知道 Git 品質會被看

自然養成完成小功能就 commit，而非悶頭寫一整週再倒出來。

2
知道 AI 透明度會被看

每次互動完順手記錄提示詞與檢查，而非事後拼湊記憶。

3
知道文件完整性會被看

寫程式當下就順手補註解說明，而非最後一天才發現 README 是空的。

知識檢定 | Knowledge Check

1
面向理解
五個評分面向分別是什麼？「AI 使用透明度」呼應哪一集談過的哪兩個關鍵字？
✅ 正確答案：
功能正確性、Git 使用品質、AI 使用透明度、程式碼品質、文件完整性。「AI 使用透明度」呼應 KP-09 談過的使用透明與理解到位。
2
輪廓判讀
組別 B 的雷達圖形狀很不對稱，這通常代表什麼樣的開發實況？
✅ 正確答案：
這組人可能真的做出了一個能動的系統（功能正確性、程式碼品質尚可），但整個開發過程完全沒有留痕——commit 紀錄稀疏、PROMPTS.md 潦草帶過，導致 Git 品質與 AI 透明度偏低。
3
觀念應用
為什麼「程式碼能跑」不足以保證專案總評高分？
✅ 參考答案：
五個面向是分開檢視的，功能正確性只是其中之一。即使程式能跑（功能正確性高），若 Git 使用品質、AI 使用透明度、文件完整性等面向嚴重偏低，仍會把整體評價往下拉，形成不對稱、不飽滿的評分輪廓。

總結回顧 | Summary

五個評分面向不是額外的負擔，是把前面幾集所有規定收攏成的一張自我檢查表。
功能正確性是底線，Git 使用品質跟 AI 使用透明度是過程的證據，程式碼品質跟文件完整性是能不能讓別人看懂的關鍵。

把五個面向內化成日常習慣，遠比截止前臨時抱佛腳有效。
