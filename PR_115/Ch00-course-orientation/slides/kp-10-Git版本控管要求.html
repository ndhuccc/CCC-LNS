2commit 是「證據」，不只是「習慣」 | Commits as Evidence

很多同學以為 commit 只是「存檔」，跟 Ctrl+S 差不多——不是。commit 帶著時間戳記，一旦推上去，時間無法偽造回去，它記錄的是「這個功能是在哪一天完成的」。

整學期只有 1 個 commit（12/27 晚上）

不管程式碼多漂亮，這個時間戳記本身就是巨大的紅旗：它在說「整學期什麼都沒做，最後一晚才生出來」。

從第 10 週開始每週穩定幾筆

訊息清楚（如「新增資料前處理模組」）——這串歷史就是持續開發的鐵證，時間軸自己會說話。

3兩種節奏，同樣總量，完全不同的故事 | Same Total, Different Story

📊 圖 1：兩種 commit 節奏比較
組別 A 總計 50 次、組別 B 總計 52 次——總量幾乎一樣，但呈現出來的故事完全相反。

4量化健康度：commit 分散係數 | The Dispersion Ratio

$$R = \frac{\text{最後兩週 commit 數}}{\text{全部 commit 數}}$$ 數字越接近 0，開發過程越分散健康；越接近 1，代表幾乎都是最後衝刺生出來的。

組別 A

最後兩週 $5+3=8$ 次，全部 50 次：

$$R_A = \frac{8}{50} = 0.16$$

組別 B

最後兩週 $15+22=37$ 次，全部 52 次：

$$R_B = \frac{37}{52} \approx 0.71$$

16% 對 71%，這就是「持續開發」跟「假裝持續開發」的量化差距。若你們組算出的 $R$ 超過 0.5，代表該提早展開行動了。

知識檢定 | Knowledge Check

1
規則理解
為什麼「整學期只有 1 個 commit」會是一個危險訊號，即使程式碼本身沒問題？
✅ 正確答案：
commit 的時間戳記無法偽造，只有一筆且集中在截止前，代表整個學期沒有持續開發的紀錄，違反「需有足量、有意義的 commit，不可截止前一次性上傳」的規定，即使程式碼品質再好，也無法證明是持續完成的過程。
2
量化計算
若某組全部 commit 60 次，最後兩週有 42 次，$R$ 值是多少？該不該警覺？
✅ 正確答案：
$$R = \frac{42}{60} = 0.7$$ 超過 0.5，屬於接近組別 B 的高風險節奏，應提早檢視是否把大部分工作壓到最後才做。
3
README 應用
README 規定要包含哪三項？它們分別對應讀者心中的哪三個問題？
✅ 參考答案：
專案目標對應「這是要解決什麼問題？」；如何執行對應「我要怎麼讓它跑起來？」；系統架構說明對應「它內部是怎麼組成的？」。三者齊全，陌生讀者才能不靠你口頭解釋就看懂整個專案。

總結回顧 | Summary

commit 歷史不是給自己看的存檔紀錄，是給別人看的「過程證據」。
分散、頻繁、訊息清楚的 commit，勝過再漂亮但只在截止前一次性上傳的程式碼。

時間軸不會說謊，它會替你說出真正的開發故事。
